# 个人网站开发过程总结

> 适用场景：手机电脑共用的个人数据管理类网站
> 技术栈：Vue 3 + Vite + IndexedDB + GitHub Pages
> 日期：2026-11-01

---

## 一、项目概述

家常菜入门指南 — 一个个人使用的厨房知识库网页应用，核心功能是菜品与食材的双向关联导航。数据存储在浏览器本地（IndexedDB），通过 GitHub Pages 部署，手机和电脑均可访问。

### 核心特点

| 特点 | 说明 |
|------|------|
| 纯前端 | 无后端服务器，数据存浏览器本地 |
| 双向关联 | 菜品↔食材互相跳转 |
| 个人专属 | 可自由增删改，打造个人知识库 |
| 跨端使用 | 电脑+手机均可访问，支持 PWA 离线 |
| 零成本部署 | GitHub Pages 免费托管 |

## 三、各阶段开发要点

### Phase 1: 基础设施搭建

**关键决策：**

| 决策 | 原因 |
|------|------|
| Hash 路由 | GitHub Pages 是纯静态托管，不支持服务端路由回退 |
| IndexedDB + Dexie.js | 容量大、支持结构化查询，Dexie 封装简化开发 |
| Pinia 状态管理 | Vue 3 官方推荐，轻量且类型友好 |
| 自定义 CSS | 不引入 UI 框架，保持轻量和风格可控 |
| vite-plugin-pwa | 离线支持 + 手机安装为 App |

**文件结构：**
```
src/
├── assets/           # 全局样式
├── components/       # 共享组件（导航、表单、备注等）
├── views/            # 页面组件（每个路由对应一个）
├── router/           # 路由配置
├── stores/           # Pinia 状态管理
└── db/               # Dexie 数据层（database.js + models.js + import-data.js）
```

**踩坑记录：**
- `browserslist` 不能用 `Android Chrome >= 80`，要用 `ChromeAndroid >= 80`
- Vue 模板中不能用字符串拼接做对象 key（如 `:class="{ 'diff-' + d: true }"`），要用函数返回字符串

### Phase 2: 食材模块

**食材详情页 8 大信息模块：**
1. 介绍 — 基本信息、营养价值
2. 品种 — 表格展示不同品种
3. 购买/挑选 — 挑选要点、避坑提示
4. 储存 — 不同方式的保存期限
5. 处理 — 清洗、去皮、切法等操作
6. 相关菜品 — 点击跳转
7. 营养成分 — 每 100g 的营养数据
8. 个人备注 — 记录使用心得

**关键实现：**
- 动态表单组件支持新增/编辑
- 分类标签栏支持 9 大分类切换
- 桌面端传统分页，移动端加载更多
- 图片上传转 base64 存入 images 表

### Phase 3: 菜品模块

**多维度分类标签体系：**

| 维度 | 示例 |
|------|------|
| 烹饪方式 | 蒸、煮、炒、卤、烤、炸、烘焙、煎、炖、焖、拌、焗 |
| 荤素/场景 | 荤菜、素菜、下酒菜、宝宝辅食、减脂餐 |
| 菜系/地域 | 家常、东北、山西、川菜、粤菜、湘菜 |
| 菜品类型 | 凉菜、热炒、汤羹、主食、甜点（主分类） |
| 用餐时段 | 早餐、午餐、晚餐、夜宵 |
| 自定义标签 | 用户自由输入 |

**关键实现：**
- 标签筛选支持多维度叠加（取交集）
- 菜品删除时级联删除关联数据（关联表、备注、收藏、浏览记录、图片）
- 食材清单中每个食材可点击跳转到食材详情

### Phase 4: 双向关联 + 选菜匹配

**匹配算法核心思路：**

```
1. 查询 dish_ingredients 表中 ingredientId 在已选列表中的所有记录
2. 按菜品分组，统计每个菜品匹配了几个食材
3. 按匹配数降序排列
4. 批量加载菜品详情
```

**匹配度标识：**
- 完美匹配（5/5）：绿色标签
- 大部分匹配（4/5）：橙色标签
- 部分匹配（3/5）：橙色标签
- 少部分匹配（2/5）：灰色标签

### Phase 5: 个人中心

**四大入口：**
- 收藏 — 收藏的菜品列表
- 浏览记录 — 自动记录最近浏览，最多 50 条
- 学习进度 — 已做过/想做列表 + 备注
- 设置 — 版本管理 + 数据导出/导入/重置

**浏览记录机制：**
- 每次打开详情页自动记录
- 同一食材/菜品重复浏览更新时间而非新增
- 超过 50 条自动删除最早的

### Phase 6: 图片与视频

**图片存储策略：**
- 图片以 base64 存入 IndexedDB 的 images 表
- 实体字段只存 imageId（指向 images 表）
- 列表页不加载图片，详情页按需加载
- 导出 JSON 时 images 表随数据一起导出

**视频方案：**
- 视频不存文件，以 URL 字符串存于实体字段
- 详情页展示视频区域，点击跳转到平台播放

### Phase 7: 初始数据填充

**数据来源：**
- 食材营养数据：中国食物成分表、USDA FoodData Central
- 菜谱内容：下厨房、豆果美食、美食杰等菜谱网站
- 部分数据由开发者根据烹饪经验整理

**数据生成方式：**
- 编写 `generate-data.js` Node.js 脚本
- 脚本输出 JSON 文件到 `data/import-data.json`
- 复制到 `public/import-data.json`
- 应用启动时自动检测空数据库并导入

**数据校验：**
- 食材数量 ≥ 100
- 菜品数量 ≥ 500
- 每个食材 8 大模块完整
- 菜品食材关联正确
- 分类标签值在预设范围内

### Phase 8: 部署上线

**部署方式：** 推送 `dist` 目录到 `gh-pages` 分支

**步骤：**
1. `npm run build` 生成 dist 目录
2. 在 dist 目录初始化独立 git 仓库
3. 推送到远程仓库的 gh-pages 分支
4. GitHub Pages 自动发布

**踩坑记录：**
- 仓库名以 `-` 开头导致 Pages 设置页 UI 异常
- `actions/configure-pages@v5` 在 Pages 未启用时会失败
- 最终改用 `gh-pages` 分支方式部署更简单
- **部署方式要匹配**：如果 Pages 配置为"Deploy from a branch"（gh-pages 分支），工作流中的 `actions/deploy-pages@v4` 步骤会失败，因为部署来源不匹配。此时工作流只需做构建验证，不需要 deploy 步骤
- **Service Worker 缓存旧版本**：PWA 的 Service Worker 会缓存 JS 文件，每次更新后用户需要清除缓存才能看到新版本。建议配置 `NetworkFirst` 策略或提示用户清除缓存

## 四、复用指南

### 快速启动新项目

如果你要开发类似的个人网站（手机电脑共用、纯前端、本地数据），可以按以下步骤：

**1. 项目初始化**
```bash
npm create vite@latest my-app -- --template vue
cd my-app
npm install vue-router pinia dexie vite-plugin-pwa
```

**2. 配置 vite.config.js**
- 添加 PWA 插件
- 配置 `base: './'`（相对路径，适配 GitHub Pages）
- 配置 manifest（名称、图标、主题色）

**3. 搭建数据层**
- 定义 IndexedDB 表结构（database.js）
- 编写数据模型（models.js）
- 编写初始数据导入脚本（import-data.js）

**4. 开发页面**
- 先搭路由和布局
- 再逐个开发功能模块
- 每个模块：列表页 → 详情页 → 增删改

**5. 部署**
- `npm run build`
- 推送 dist 到 gh-pages 分支
- 配置 GitHub Pages 使用 gh-pages 分支

### 关键经验总结

| 经验 | 说明 |
|------|------|
| 需求文档先行 | 详细的需求和设计文档让开发速度提升 3-5 倍 |
| 分阶段开发 | 每阶段可独立验证，避免一次性开发导致问题难定位 |
| 数据驱动设计 | 先设计数据模型，再开发页面，避免返工 |
| 原型图辅助 | HTML 原型图让 UI 讨论更直观，减少沟通成本 |
| 轻量技术栈 | Vue 3 + Vite + IndexedDB 足够支撑个人项目，无需后端 |
| GitHub Pages 部署 | 免费、稳定、零运维，适合个人项目 |
| Hash 路由 | 必须使用，否则 GitHub Pages 刷新会 404 |
| 数据自动导入 | 首次启动自动检测空数据库并导入初始数据 |
| 手动数据同步 | 各设备数据独立，通过导出/导入 JSON 实现同步 |
| **部署方式匹配** | gh-pages 分支部署时，工作流不需要 deploy 步骤，只需构建验证 |
| **PWA 缓存策略** | Service Worker 会缓存旧版本，需配置 NetworkFirst 或提示用户清除缓存 |
