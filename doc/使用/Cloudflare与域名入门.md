## 一、Cloudflare 是什么

### 1.1 一句话定义

Cloudflare 是一家全球性的「网站加速 + 安全防护」云服务商。可以把它想象成网站前面的**「全球前台 + 保安 + 加速器」**——所有访问者先到 Cloudflare 的节点，再由它转发给网站。

它最核心的能力是**反向代理**：网站内容实际放在别处（如 GitHub、Cloudflare Pages），但对外都从 Cloudflare 的网络进出，于是它顺便帮你做加速、防护和访问控制。

### 1.2 全球边缘网络（为什么快）

Cloudflare 在全球有 300+ 个数据中心（「边缘节点」）。用户访问时就近接入最近的节点，而不是直连源站，因此**无论在哪都更快**。这也是它被称为 **CDN（内容分发网络）** 的原因。

### 1.3 相关免费产品

| 产品 | 作用 | 类比 |
|------|------|------|
| **DNS** | 域名解析，把 `cook.你的域名.com` 指向站点 | 电话簿 |
| **CDN / 加速** | 全球节点就近分发，访问快 | 快递前置仓 |
| **SSL / HTTPS** | 自动免费证书，加密访问 | 加密信封 |
| **DDoS 防护 / WAF** | 挡住攻击和恶意流量 | 保安防火墙 |
| **Cloudflare Pages** | 静态网站托管（对标 GitHub Pages） | 免费店面 |
| **Cloudflare Access** | 登录门禁（邮箱验证码 / Google 登录） | 门禁闸机 |
| **Cloudflare Tunnel** | 把本机服务安全暴露到公网 | 私家隧道 |
| **Workers / R2** | 边缘函数 / 对象存储（本站用不到） | 可编程前台 / 仓库 |

> 本站私有化部署只用到三样：**DNS + Pages + Access**。

### 1.4 免费额度（个人够用）

| 项目 | 免费额度 |
|------|----------|
| DNS | 免费 |
| HTTPS 证书 | 免费且自动续 |
| Cloudflare Pages | 免费（每月 500 次构建，无限带宽） |
| Cloudflare Access / Zero Trust | 免费（≤ 50 个用户） |

> 唯一需要花钱的是**域名本身**（约 ¥30–100/年，在域名注册商处购买）；把 DNS 托管到 Cloudflare 免费。

### 1.5 与 GitHub Pages 的关系

Cloudflare Pages 与 GitHub Pages 是**同类**（静态托管），但 Cloudflare 多了访问控制、且支持私有仓库免费部署：

| 对比项 | GitHub Pages | Cloudflare Pages |
|--------|--------------|------------------|
| 定位 | 静态托管 | 静态托管（同类） |
| 访问控制 | ❌ 无 | ✅ 有（Access） |
| 私有仓库免费部署 | ❌ 不支持 | ✅ 支持 |
| DNS / CDN / HTTPS | 有 | 有（且更强） |

> 不是「换掉 GitHub」，而是「把**发布托管**交给 Cloudflare」：**GitHub 管代码，Cloudflare 管分发与门禁**。

### 1.6 免费的边界：什么免费、什么付费、为什么

Cloudflare 的核心功能免费，但**并非「完全免费」**。更准确的理解是：**把域名的「钥匙」（DNS 托管权）交给它，它就免费给你配保安**；但域名本身要自己买。

| 环节 | 实际动作 | 花钱吗 |
|------|----------|--------|
| 告诉它一个地址 | 把域名添加到 Cloudflare | — |
| 交出钥匙 | 把域名 DNS 托管权交给 Cloudflare（改 NS） | 免费 |
| 它配保安 | DNS、加速、证书、门禁（Pages / Access） | 免费 |
| 域名本身 | 在注册商处购买 | ¥30–100/年 |

**你要用的三样（DNS + Pages + Access）全在免费范围内**（详见 1.4）。

**以下功能才收费（个人基本用不到）：**

| 付费功能 | 适用场景 |
|----------|----------|
| 高级 WAF / Bot 管理 | 企业级防护 |
| 更大配额 / Durable Objects | 重后端、高并发 |
| 企业版 Private Pages / 高级 SSO / SLA | 大公司需求 |
| 负载均衡 / Argo 等增值 | 大型架构 |

**它凭什么免费？** 典型 **freemium（免费增值）** 模式：

- 免费套餐吸引海量用户 → 网络规模更大、威胁情报更多 → 反哺平台
- 真正赚钱的是**企业版客户**；个人免费用户其实在「搭便车」
- 规模效应让人均成本极低，送一点资源毫无压力

**免费版的边界（须知）：**

| 注意点 | 说明 |
|--------|------|
| 域名要自己买 | Cloudflare 不送域名 |
| 有「合理使用」限制 | 免费 CDN 不欢迎当「免费视频大水管」；纯静态个人应用无碍 |
| 数据经过 Cloudflare | 流量元数据会被记录（隐私考量，个人项目无妨）|
| 免费 ≠ 无上限 | 超量 / 高级功能仍需付费 |

> 一句话：**你把域名的钥匙交给它，它就免费给你配保安；真正花钱的只有「域名」这一个。**

## 二、域名与子域名

### 2.1 基础概念

| 层级 | 例子 | 数量 | 费用 |
|------|------|------|------|
| 主域名 | `example.com` | 你买的这一个 | 买一次 |
| 子域名 | `cook.example.com`、`blog.example.com`… | **无限个** | **免费** |
| 路径 | `example.com/cook`、`example.com/blog` | 无限 | 免费 |
| 端口 | `example.com:8080` | — | 仅适合本地调试 |

### 2.2 一个域名能承载多个网站

**只买一次 `example.com`，就能派生出无数个子域名，每个子域名可指向完全不同的网站/项目。** 子域名不额外收费。

### 2.3 三种「一域多站」方式对比

| 方式 | 长相 | 适合场景 |
|------|------|----------|
| **子域名**（推荐） | `cook.example.com`、`notes.example.com` | 各自独立的项目，互不干扰，可配独立 HTTPS 与登录策略 |
| **子路径** | `example.com/cook`、`example.com/notes` | 内容相关的小站点；静态应用需配 `base` 路径，稍麻烦 |
| **端口** | `example.com:8080` | 只适合本地调试，公网站点不实用 |

> 想做多个独立网站，用**子域名**最干净。

### 2.4 成本小结

- 主域名买一次，每年续费一次（约 ¥30–100/年）
- **子域名免费且无数量上限**，以后想做新项目，直接 `xxx.你的域名.com` 即可

## 三、域名 ≠ 服务器（常见误解）

买域名和买/租服务器是**两件完全不同的事**——买域名**不等于**获得某个服务器的使用权限。域名本身不附带任何服务器。

| 概念 | 类比 | 是什么 | 花钱吗 |
|------|------|--------|--------|
| **域名** | 门牌号「幸福路 8 号」 | 一个名字 / 地址标识 | 年费（¥30–100/年）|
| **DNS** | 电话簿 / 导航 | 把门牌号「翻译」成实际地址 | 一般免费 |
| **服务器 / 托管** | 实际的房子 | 存内容、对外服务的机器 | 租用 or 免费静态托管 |

三者关系：**域名 →（通过 DNS 指向）→ 服务器 / 托管**。域名只是名字，真正干活的是服务器，DNS 是中间的桥。

**容易混淆的原因**：很多服务商把域名和主机打包卖（「买域名送空间」），让人误以为是一回事。但实际上它们始终独立——同一个域名今天指向 A 服务商，明天可改指向 B；同一台服务器也可被多个域名同时指向。

> ⚠️ 澄清：**买一个域名，得到的只是「这个名字归你用」的权利，不会附带任何服务器。**

## 四、它们如何配合（本站场景）

假设你购买了 `example.com`：

```
手机 / 电脑（外网）
        │  https://cook.example.com
        ▼
Cloudflare DNS（解析到 Cloudflare 网络）
        ▼
Cloudflare Access（登录门禁：邮箱验证码）
        ▼
Cloudflare Pages（cook-guide 静态站点）
        ▼
浏览器 IndexedDB（个人数据，本地存储）
```

| 子域名 | 用途 | 承载方式 |
|--------|------|----------|
| `cook.example.com` | 家常菜入门指南（cook-guide） | Cloudflare Pages 项目 A |
| `blog.example.com` | 其他站点（示例） | Cloudflare Pages 项目 B |
| `notes.example.com` | 再一个站点（示例） | Cloudflare Pages 项目 C |

每个子域名都可以：绑定不同 Pages 项目、配置各自的 Access 登录策略、自动获得独立免费 HTTPS 证书。

### 4.1 谁在当「服务器」

**本方案的服务器是 Cloudflare，不是你的电脑。**

| 角色 | 谁扮演 | 干什么 |
|------|--------|--------|
| 存代码 | **GitHub** | 保存源代码 |
| 服务器（托管） | **Cloudflare Pages** | 真正对外提供网站、全球分发 |
| 门禁 | **Cloudflare Access** | 登录鉴权，挡住别人 |
| DNS | **Cloudflare** | 域名解析 |
| 你的电脑 | **你** | 只在改代码 / 更新时用一下 |

你的电脑只在**更新网站**时用到：

1. 改 `src/` 里的代码
2. `git push` 推到 GitHub
3. Cloudflare 自动拉取、构建、发布（**在 Cloudflare 服务器上跑，不用你的电脑**）

推送完成后，电脑关机也不影响网站运行——你甚至可以不在本地构建，把 `npm run build` 也交给 Cloudflare。

> 对比：若采用「本地 / 局域网」方案，才需要**自己的电脑当服务器并常年开机**；本方案不需要。

### 4.2 Access 负责什么，你的应用不用写什么

Cloudflare Access 的本质是「**认证即服务**」——把登录与用户管理整个外包出去，你的应用代码可以做到**零用户管理、零密码、零登录页**。

**你原本以为要自己写的东西，其实都不用：**

| 需求 | 传统自建 | 用了 Cloudflare Access |
|------|----------|------------------------|
| 用户管理 | 建用户表 + 管理后台 | ❌ 不用，在 Cloudflare 后台管理名单 |
| 登录界面 | 自己写登录页 | ❌ 不用，Cloudflare 提供现成登录页 |
| 存储用户密码 | 自己哈希加盐、存库 | ❌ 不用（验证码 / 第三方登录不存密码）|
| 修改密码 / 找回密码 | 自己写整套流程 | ❌ 不用（验证码方式没有长期密码）|
| 维护个人信息 | 自己做资料页 + 存库 | ❌ 不用，身份信息由 Cloudflare 持有 |
| 防撞库 / 限流 | 自己做 | ❌ 不用，Cloudflare 边缘兜底 |

**加了 Access 之后，你的应用代码一行认证逻辑都不用加**，流程如下：

```
用户输入 cook.你的域名.com
   ↓
Cloudflare 拦截 → 弹出 Cloudflare 的登录页（不是你写的）
   ↓
用户输邮箱 → 收验证码 → 填验证码（或点 Google 登录）
   ↓
验证通过 → 放行 → 请求才到达 cook-guide
```

> 你的应用从头到尾「不知道」发生过登录，只负责被访问到之后照常运行。

**几个技术细节：**

- **应用感知不到用户身份**：Access 放行后，身份（JWT）默认不会自动传给纯前端应用。单用户无所谓；将来要做"多用户数据隔离"，才需用一个 Worker 读取 Access 注入的 `Cf-Access-Jwt-Assertion`，按邮箱区分数据。
- **"手机登录"**：在手机上用**邮箱验证码**或 **Google 账号**登录都很方便；但 Access 原生**没有**"手机号 + 短信验证码"登录（要短信得接第三方 IdP，个人场景没必要）。
- **"修改密码"需求消失**：用的是**一次性验证码**，没有长期密码可改；若想要"真账号"，可选 Google 登录，密码交给 Google 管。

**什么时候才需要自建用户系统？** 只有出现以下需求时：多用户且数据要隔离、需要在应用内维护用户资料、需要手机号短信登录或复杂权限体系。**单用户 + 只要挡住别人，完全用不到。**

### 4.3 为什么 Access 必须要有域名

Cloudflare 的所有能力（加速、防护、鉴权）都建立在「**接管你的域名解析**」之上——**没有域名，就没有接管的入口**。具体三点：

1. **Cloudflare 的入口在 DNS 层**：你把域名的 DNS 交给 Cloudflare 后，访客流量先到 Cloudflare 节点，它才能站在「你和访客之间」做事。
2. **Access 以「域名对应的应用」为单位**：每条策略都要绑定一个应用域名（如 `cook.你的域名.com`），且 Cloudflare 需要**验证该域名确实归你所有**（通过 DNS / NS 记录），否则任何人都能声称"保护别人的网站"。
3. **`pages.dev` 是 Cloudflare 自己的域名**：你无权修改它的 DNS，也不能在它上面挂 Access 策略；要加门禁，只能绑一个**自有域名**。

> 类比：域名是「门牌号 / 房产证」，Cloudflare 是物业保安，Access 是装在门上的闸机——物业要给你装闸机，前提是「你确实住这儿」（域名归属验证）。

**取舍：要不要域名**

| 目标 | 需要域名吗 |
|------|:---:|
| 只是把网站托管出去（能访问就行） | ❌ 不需要，用免费的 `xxx.pages.dev` |
| **要登录鉴权 / 门禁** | ✅ **必须**，Access 只能挂在自有域名上 |
| 要好记、体面的地址 | ✅ 需要 |

> 一句话：**不接受网站公开 → 要用 Access → Access 必须有域名**，两者是绑定的；不想要域名也行（白嫖 `pages.dev`），但那样就没有登录门禁。

## 五、小结

| 关键词 | 一句话记忆 |
|--------|-----------|
| Cloudflare | 免费的「全球加速 + 安全门禁」平台 |
